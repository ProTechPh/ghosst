# Ghosst auth Wi-Fi/DNS/WAF runbook

## What the error means

The text **“You do not have access to this. If you use a VPN or Private DNS,
turn it off and try again.”** was generated by Flutter's old generic HTTP 403
message in `lib/api/api_exception.dart`. It was not a PHP response string and
did not prove a DNS failure.

`POST /v1/auth/google` itself has no 403 path, and the PHP API contains no ASN,
VPN, proxy, or IP-reputation middleware. A 403 on that route therefore comes
from Cloudflare or the hosting edge before PHP runs. Google Play Services errors
use a separate `GoogleSignInException` path.

The client now reports non-JSON 403 responses as `gateway_blocked`, keeps API
permission errors separate, and logs redacted transport/HTTP diagnostics in
debug builds:

```text
{"event":"api_error","diagnostic":"dio=badResponse status=403 cfRay=... body=...","requestId":"...","method":"POST","path":"/auth/google","attempt":0}
```

Use the request ID to find `[device] req=<id> ...` in the PHP error log and the
Cloudflare Ray ID to find the exact Security Event.

## Client behavior

- Primary, refresh, and API control probes send
  `User-Agent: GhosstApp/1.0 (Android)`.
- System DNS is tried first with a short timeout. DNS failure, an empty answer,
  a stalled TCP/TLS attempt, or failure of every returned address triggers
  Cloudflare JSON DoH and then Google JSON DoH.
- DoH bootstrap uses the providers' public anycast IPs, normal TLS certificate
  validation, and the provider hostname for SNI. A provider deadline force-closes
  its HTTP client before the next provider is tried.
- The API TLS handshake always uses `ghossthub.com` for SNI and certificate
  validation, even when DoH supplied the IP. Late TLS results are destroyed;
  `dart:io` cannot cancel an already-started `SecureSocket.secure()` handshake,
  so a permanently stalled native handshake falls back to the OS TCP timeout.
- HTTP 403 does not trigger DoH: an HTTP response proves DNS/transport worked,
  and changing resolvers does not change an edge policy decision.
- Debug logs never include request bodies, authorization headers, passwords,
  Google ID tokens, access tokens, or refresh tokens.

## Cloudflare Browser Integrity Check

Cloudflare Browser Integrity Check (BIC) can challenge non-browser clients. If
Security Events shows BIC/error 1010 for Ghosst, deploy the narrow rule in
[`cloudflare/ghosst-app-bic-skip.json`](cloudflare/ghosst-app-bic-skip.json).
It skips **only BIC**, only for `ghossthub.com/api/v1/*`, and only for the exact
app User-Agent. Managed WAF rules, rate limits, bot scores, and IP reputation
checks stay enabled. User-Agent is identification, not authentication.

Dashboard:

1. Open **Security → Security rules → Create rule → Custom rule**.
2. Use the expression from the JSON file.
3. Set action to **Skip** and select only **Browser Integrity Check**.
4. Place the rule before any custom Block/Challenge rules, keep request logging
   enabled, and save.

Rulesets API: obtain the `http_request_firewall_custom` entry-point ruleset ID,
then POST the JSON file to
`/client/v4/zones/$ZONE_ID/rulesets/$RULESET_ID/rules` with a zone-scoped WAF
token. No Cloudflare credentials are stored in this repository.

Do not whitelist PLDT/Globe/Converge ASNs wholesale. Shared/CGNAT ranges contain
untrusted users too, and an ASN exception would disable protection for far more
than this app. If the event identifies a specific managed-rule or IP-reputation
false positive, create an exception for that single rule after confirming the
Ray ID and request path.

## Standard-Wi-Fi verification checklist

1. On the test phone, disable Private DNS and WARP/VPN. Keep IPv4 enabled and
   use the ordinary PLDT/Globe/Converge Wi-Fi DNS settings.
2. Install the new debug or release build. Clear Ghosst's app data first so an
   old cached session does not hide the login path.
3. Open **Continue with Google** and complete account selection.
4. Confirm the app reaches Home and the coin balance appears.
5. In debug logcat, confirm `User-Agent: GhosstApp/1.0 (Android)`. If DoH was
   needed, expect `api_system_dns_failed` or `api_system_connect_failed`,
   followed by `api_doh_fallback` and `api_doh_connected`.
6. If it still fails, copy the `api_error` line. Check `status`, `cfRay`, and
   `requestId`; do not assume DNS from the user-facing message.
7. For `status=403`, inspect that Ray ID in Cloudflare Security Events. Apply
   only the BIC rule above when BIC is the identified source.
8. For `SocketException`, check Wi-Fi captive portal/DNS. For
   `HandshakeException`, check date/time, DNS hijacking, and TLS interception;
   never disable certificate validation to make login pass.
