# User Reels Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add gallery-video reels with self-hosted z.com files, a vertical autoplay feed, follows integration, likes, comments, reports, creator profiles, and admin moderation.

**Architecture:** The PHP API creates pending reel rows and short-lived HMAC upload tickets. The app uploads MP4 bytes directly to a small z.com PHP endpoint, then completes the row through the main API. MySQL stores metadata/social interactions; z.com stores public media. Flutter uses `video_player` with one active controller per feed.

**Tech Stack:** Flutter/Dart (`video_player`, existing `file_picker`, `dio`, `crypto`), PHP 8/PDO MySQL, z.com PHP uploader, existing website admin.

**Spec:** `docs/superpowers/specs/2026-11-25-social-features-design.md` (approved 2026-11-25), sections 13–15, 17–19, 21–22.

**Depends on:** `docs/superpowers/plans/2026-11-25-public-profiles.md` and `docs/superpowers/plans/2026-11-25-social-graph.md`.

## Global Constraints

- MP4 only; 50 MB hard cap; 60-second target; maximum 5 uploads per rolling 24 hours per user.
- No FTP credentials or `REEL_UPLOAD_SECRET` in the APK. Upload tickets live 15 minutes.
- All list endpoints paginate; feed page size is 10; comments page size is 20.
- API HTTP calls stay in `lib/services/worker_backend.dart`; direct z.com upload lives in `lib/services/reel_upload_service.dart`, mirroring `cloudinary.dart`.
- Reels auto-publish after validation; moderation is post-publication.
- Tests must not initialize a real video plugin, Firebase, MySQL, or network.
- Do not manually bump the build number or push to `main`.

## Review Focus

1. Wrong/expired/forged upload ticket, oversized file, MIME/hash mismatch, or path traversal → reject before publish; pinned in Tasks 2–3.
2. Duplicate complete/retry or same idempotency key with different payload → no duplicate reel or wrong replay; pinned in Task 2.
3. Off-screen video keeps playing/leaks controller → only active page plays and all controllers dispose; pinned in Task 5 lifecycle tests.
4. Hidden/deleted/banned creator or reel leaks into feed/profile → SQL filters exclude it; pinned in Task 4.
5. User reports illegal content or deletes own reel → report queue works and reel disappears immediately; pinned in Tasks 4, 6, and 7.

Change `idem_reserve()` to accept optional `?string $requestHash = null`; existing claim callers remain unchanged. On replay/in-flight with a supplied hash that differs, return `state='mismatch'`. Store the hash on new reservations.

Delete is an idempotent owner soft-delete. `reels_expire_pending()` marks pending rows older than 24 hours deleted and returns their IDs for signed file cleanup; it is invoked by a host cron, never by a public route.
